## 2. 확정 — 폰트

### 2.1 `.FNT` = 장면별 한자 서브셋 (사실)

```
+0x00  BE16  글리프 수 N
+0x02  BE16  0x0004        (의미 미확정, 65개 파일 전부 동일)
+0x04  14B   0x00
+0x12  N x 32B             1글리프 = 16행 x BE16 (왼쪽 픽셀이 MSB)
```
- 근거: 디스크 1의 **65개 파일 전부** `(size-18) == N*32` 성립 (위반 0건).
- 실측 잉크 박스(EVTZOAH.FNT 715자) = `x 2..13, y 1..11` → **실사용 12x11**, 셀은 16x16.
- 글리프 내용은 **한자·라틴만**. 가나는 들어 있지 않다.
- 배열 순서 = 그 장면 텍스트의 **첫등장 순서**.

### 2.2 기본 폰트 = `COMMON.DAT + 0x1068A`, 256글리프 (사실)

같은 32B 글리프가 정확히 256개 연속. 내용:

> ※ (공백) 0-9 / あ~ん / … ( ) 『 』 ！ ？ ー ＋ 。 「 」 、 ・ /
> ヲ~ン 濁音·半濁音 / 小書き가나 / A~Z / ％ /
> 상용한자 30여 자(威覚機技却究極型形撃御攻更国示銃準心性生素装体態着帝動売備標表物変防無力) / BP EXP ×

## 3. 확정 — 텍스트 인코딩 (사실)

**글리프 인덱스 스트림**. Shift-JIS도 코드표도 쓰지 않는다.

```
byte >= 0x80 : 2바이트 글자 토큰, index = ((b & 0x7F) << 8) | next
byte <  0x80 : 1바이트 제어코드
```

글리프 공간은 2층:

| index | 공급원 |
|---|---|
| `0 .. 255` | `COMMON.DAT +0x1068A` 상주 기본 폰트 (가나·숫자·기호·A~Z·상용한자) |
| `256 ..`   | 그 모듈의 짝 `.FNT` 의 `index-256` 번 글리프 |

- **경계 256의 근거**: `TWN_ZOAH.PRG` 전체 텍스트에서 index>=256 의 첫등장 순번이
  256부터 완전한 오름차순(첫등장 순서 폰트). index<256 는 순서 없이 흩어짐.
- 관측된 제어코드: `0x00`(문자열 종료/구분), `0x06`(개행). 그 외는 아직 관측 안 됨.
- **검증**: `TWN_ZOAH.PRG +0x377E0` 을 이 모델로 디코드 → 렌더 결과가
  「街の入口の横にある階段を越えて…」 / 「そのまま進めば、通路に入れるはずだよ」 +
  선택지 「ジューバの店への道」… 로 **정상 일본어**. (`work/zoah_dialog.png`)

### 3.1 PRG ↔ FNT 짝 (후보)

이름 규칙으로 유도: `FLD_xx.PRG↔FLD_xx.FNT`, `BTL_xx.PRG↔BTL_xx.FNT`,
`TWN_ZOAH↔EVTZOAH`, `TWN_CAMP↔EVTCAMP`, `TWN_CARA↔EVTCARA`, `TWN_SEEK↔EVTSEEK`,
`TWN_EXCA↔EVTEXCA`, `TWN_RUIN↔EVTRUIN`.
`*_2/_3` 배틀 모듈, `TWN_E0xx`, `FLD_C8`, `1ST_READ`, `WORLD` 의 짝은 **미확정**
(로더 코드로 확인해야 한다). `EVT0xx_x.FNT` 는 저 LBA 무비 구간에 있어 **자막 후보**.

## 7. 세션 2 (2026-08-10) — 영문판(Panzer Dragoon Saga USA) 대조

### 7.1 파일 구성은 사실상 동일 (사실)

디스크 1 기준. JP 1,693파일 / US 1,695파일, **공통 1,690개**.

| | JP만 | US만 |
|---|---|---|
| | `ANDRO.TXT`, `TITLEJ.PNB`, `TITLEJ.SCB` | `AZEL_ABS/BIB/CPY.TXT`, `TITLEE.PNB`, `TITLEE.SCB` |

공통 1,690개 중 **내용까지 같은 것 1,605개**(크기 동일), 크기가 다른 것 85개.
크기가 다른 건 전부 `PRG`(31개)·`FNT`(20개)·`COMMON.DAT`·`MOVIE.DAT`·`MENUBK.BIN`뿐이고,
모델(CGB/MCB)·음성(PCM)·무비(CPK/EPK)·배경(SCB/PNB)은 **1바이트도 안 바뀌었다**.

### 7.2 US 텍스트 = 평문 ASCII (사실)

`TWN_ZOAH.PRG US +0xB24F` 부터 `Town of Zoah\0Town of Zoah\0Holy District\0…` 이
그대로 보인다. 널 종단 문자열이 연속 배치된 **같은 테이블**이다.

- 테이블 시작 위치가 JP 0xB27F / US 0xB24F 로 **거의 같고, 앞 헤더 바이트열
  (`… 3c 1d 1a 01`)까지 동일**하다 → 같은 코드 베이스, 같은 구조.
- 디스크1 `TWN_ZOAH.PRG` US 영문 분량 = 20개 구간, 4,225 문자열, 약 88,000자.

### 7.3 문자열 테이블 문법 — 확장 (사실)

세션1 모델을 다음으로 넓힌다. 한 문자열 안에 세 종류가 섞인다.

```
b >= 0x80          2바이트 글리프 토큰  idx = ((b & 0x7F) << 8) | next
0x20 <= b < 0x80   1바이트 ASCII 문자
b <  0x20          1바이트 제어코드 (0x00 = 문자열 종단)
```

- **JP도 ASCII를 쓴다**: 대사 사이사이에 `T_SF_016.PCM` 같은 **음성 파일명 문자열이
  인터리브**돼 있다. 세션1의 census가 여기서 끊긴 원인이기도 하다.
- 이 PCM 파일명 열이 **JP·US에서 순서까지 완전히 같다**
  (`T_SF_016 → T_EG_058 → T_SF_017 → T_EG_059 → T_SF_018 → …`)
  → **JP↔US 대사 정렬의 앵커**로 쓸 수 있다.
- 관측 제어코드: JP `0x16`,`0x1B` / US `0x03`,`0x05`,`0x09`,`0x18`. 아직 전수 아님.

### 7.4 기본 폰트는 JP·US 완전 동일 (사실)

US `COMMON.DAT +0x10EAA` 에 세션1이 찾은 256글리프가 **바이트 단위로 똑같이** 들어 있다
(JP `+0x1068A`). 즉 US판도 가나·한자 폰트를 그대로 들고 있고, **영문 소문자는 여기 없다**.
→ US판 영문 폰트는 별개 자산이며 **위치 미확정**(§7.6).

`COMMON.DAT` 가 US에서 정확히 +2,080 B(=65×32) 커졌지만, 그 증가분은 폰트 뒤가 아니라
`0x1617` 이후 상이 구간 안에 있고 32B 글리프 배열로 렌더하면 노이즈다 → 폰트 아님.

### 7.5 ★FNT 글리프 수 확장은 실제로 동작한다 (사실)

US `BTL_A5.FNT` = 48글리프(JP) → **54글리프**. 늘어난 6자를 렌더하니
「英 語 版 対 応 蒼(玉)」 — 영문판 빌드가 그 장면 폰트에 글자를 **추가**한 것이다.
20개 FNT가 이렇게 늘거나(+4~6자) 줄었다(`FLD_B5.FNT` −48자, `FLD_D2.FNT` −14자).

→ **장면별 `.FNT` 는 글리프 수를 바꿔도 되는 자산**이라는 공식 빌드발 증거.
   한글 음절 글리프를 FNT에 얹는 길(2바이트 토큰 idx 256+ 사용)이 열려 있다.
   ⚠ 다만 로더 버퍼·VRAM 상한은 여전히 미측정 — 어디까지 늘려도 되는지는 별개 문제.

### 7.7 ★세션1 모델 정정 — `0x20~0x7F` 는 ASCII 가 아니라 **1바이트 글리프 토큰**

US 텍스트가 평문 ASCII 로 읽히길래 JP 도 같은 자리를 ASCII 로 읽었는데 **틀렸다**.
JP `TWN_ZOAH.PRG` 실측 네 곳이 전부 글리프 해석만 말이 된다.

| 오프셋 | 바이트 | ASCII 해석 | 글리프 해석 (index = 바이트값) |
|---|---|---|---|
| 0xC663 | `3C` | `<` | **`)`** (index 60) — 앞 문장의 닫는 괄호 |
| 0xC8E5 | `20 800D 8020 803C` | `␣いな)` | **`ないな)`** (index 32 = `な`) |
| 0xE7C0 | `23` | `#` | **`ね`** (index 35) |
| 0xF0F3 | `3A` | `:` | **`…`** (index 58) |

기본 폰트가 あいうえお 순이라 **index ≥ 0x20 인 글자(`な`~`ン`)만 1바이트로 쓸 수 있고**,
그래서 실제 사용이 드물다(첫 구간 757문자열 중 9건).
→ 한글화 때 이 구간 슬롯을 한글로 갈면 **자주 쓰는 음절을 1바이트로** 넣을 수 있다.

`T_SF_016.PCM` 같은 **파일명 문자열만 진짜 ASCII**다. 렌더 대상이 아니라 파일명 인수라
소비자가 다르다. 한글화 때 **건드리면 안 되는 문자열**이다.

### 7.8 기본 폰트 매핑표 확정 — `tools/basemap.py`

256글리프를 16열 시트로 렌더해 유니코드 표를 작성했다. 실측 보조 사실:
빈 글리프는 index 1 하나뿐, index 0 과 255 가 같은 비트맵(`※`), index 253·254 는
`BP`·`EXP` 합자.

검증: 테이블 첫 문자열 `80 8C 80 53 80 24 81 00` → `ゾ ア の 【0】` = 「ゾアの街」,
US 같은 자리 = `Town of Zoah`. ✅

이제 `tools/dump_text.py` 로 JP 대사를 일본어 그대로 읽을 수 있다
(장면 FNT 한자는 `【n】` 자리표시자).

### 7.9 JP 텍스트 구간 (디스크1 `TWN_ZOAH.PRG`)

첫 구간 = `0xB27F .. 0xFF5F`, **757 문자열 / 9,659 글자**

### 7.10 JP 구간 목록 확정 — `tools/regions.py`

디스크1 `TWN_ZOAH.PRG` **22구간 / 5,534 문자열 / 48,097 글자**

### 7.12 예산 — JP vs US (사실)

| | 바이트/글자 | 22구간 합계 |
|---|---:|---:|
| JP | 1.98 B/자 | 95,083 B / 48,097자 |
| US | 1.07 B/자 | 74,993 B / 69,797자 |

US는 **글자 수가 JP의 1.45배인데 바이트는 0.79배**다(1바이트 토큰).
구간별 US/JP 바이트 비 = **0.94x ~ 1.35x**, `TWN_ZOAH.PRG` 자체도 +14,507 B.
→ 공식 영문판은 **구간 크기를 바꿔가며** 텍스트를 넣었다. 바이트 제약은 느슨하다.
   (단 이건 «구간» 단위 사실이고, 개별 문자열 제약은 §7.13 참고.)

한글화 환산: 한글은 JP 처럼 2바이트 토큰이 주력이므로 JP 예산(95 KB) 수준이면 되고,
자주 쓰는 음절을 1바이트 슬롯(§7.7)에 배치하면 더 준다.

### 7.13 문자열별 포인터 배열은 «없다» (사실, 소극적 증거 포함)

첫 구간 문자열 시작 오프셋 13개의 **차분열**(9,9,7,1,7,1,9,7,1,7,1,11)을
파일 전체에서 BE32·LE32·BE16·LE16 으로 찾았다 → **네 형식 모두 0건**.
로드 베이스 상수를 허용해 구간 시작 8개를 동시에 설명하는 공통 베이스도 **0건**.

보강 증거: 「は【185】わねえんだとさ」 같은 **똑같은 문장이 지명마다 통째로 중복 저장**돼
있다. 포인터가 있었다면 공유했을 것이다. 그리고 대사 사이에 음성 파일명이 인터리브된
배치도 «스크립트가 순서대로 소비한다»는 그림에 맞는다.

→ **순차 소비 가설**: 문자열 길이를 바꿔도 뒤가 밀리기만 하면 된다.
   ⚠ 아직 «가설»이다. 구간 시작 주소가 어디서 참조되는지는 SH-2 코드로 확인해야 한다.

### 7.14 ★미해독 잔재는 한 구간에 몰려 있다

미해독 리드 바이트가 든 문자열 1,139개 중 **1,097개가 `0x22862..0x279C5` 한 구간**
(그 구간 대사의 55%)이고, 나머지 21개 구간은 **0~8%, 대개 1~2%** 다.

그 구간의 정체 = 지명마다 「◯◯の【155】」 + 「は【185】わねえんだとさ」가 반복되는
**소문/정보 목록**. 반복 사이에 `9B 00` 이 0,1,2개씩 끼거나 뒷 문장이 `B9`(=`81 B9`의
뒷바이트)부터 시작한다. 앞 문자열은 예외 없이 글리프 411(`【155】`)로 끝난다.

즉 **전역 문법 문제가 아니라 그 구간 특유의 구조**다. 포인터로 접근되는 슬롯에
이전 데이터 잔재가 남은 것으로 보이지만 **확정 못 했다**.
⛔ 처음에 이 바이트들을 「미해독 제어코드」로 적었는데, 실제로는 대부분
   **2바이트 토큰의 뒷바이트를 리드로 잘못 센 것**이었다(`81 9B` = 글리프 411).
   raw 바이트 스캔으로 «제어코드 후보»를 세지 말 것 — 토큰 경계를 따라가야 한다.

### 7.15 ★`0x22862` 구간 규명 완료 — 선택지 메뉴의 «고정 슬롯 배열»

§7.14 의 잔재 정체를 확정했다. **버그도 미해독 제어코드도 아니고, 고정 크기 슬롯의
남는 꼬리에 남은 죽은 바이트**다.

**US 대응이 결정적이었다.** PCM 앵커(`T_JB_040.PCM`)로 자리를 맞추니 US 같은 자리가

```
About the Empire / About the Dragon / About the Town of Zoah /
About the Liberal District / About Jubas / About the Holy District /
About the 'Guardian Fire' / About the High Priest / About the Seekers /
About Uru / About Tobitama / Quit
```

JP 는 `帝国の噂 / ドラゴンの噂 / ゾアの街の噂 / … / 噂をやめる` 였다.
**대화가 진행되며 이미 물어본 주제가 빠진 목록이 여러 벌 저장**돼 있어 반복이 많다.
(덕분에 `【155】` = `噂`, `【599】` = `巣`, `【185】` = `使` 도 확정됐다.)

**슬롯 구조 (사실)**: 항목 시작 오프셋이 **정확히 등간격**이다.

```
0x23DF1 帝国の噂        (9 B)   +31
0x23E10 ドラゴンの噂     (13 B)  +31
0x23E2F ゾアの街の噂     (13 B)  +31
   …                          ×12항목
0x23F46 噂をやめる  ← Quit
```

`0x22862..0x279C5` 구간 전체에서 등간격 런 **73개, 항목 473개**.
슬롯 크기는 **31 B 가 주력**, 그 밖에 40·42·64·65·73·77 B.

**잔재 검증 (사실)**: 「잔재라면 앞쪽 데이터의 부분 문자열일 것」이라는 예측을 검사했다.
미해독 리드 바이트가 든 문자열 1,139개 중 **1,128개(99%)** 가 같은 구간 앞쪽 4 KB 안에
**똑같은 바이트열(종단 포함)로 존재**한다. → 잔재 가설 확증.

★**한글화 함의**: 이 항목들은 **슬롯 크기 제약**을 받는다. 31 B 슬롯이면 종단 포함
31 B 안에 들어가야 하고, 2바이트 토큰만 쓰면 **15글자**다. 구간 단위로는 크기를 바꿔도
되지만(§7.12) 슬롯 배열 안은 다르다 — 여기는 **제자리 예산**이다.

부수 사실: 전체 대사 4,675개 중 **63%(2,965개)가 앞쪽에 동일 바이트열**을 갖는다.
같은 문자열이 여러 번 저장돼 있다는 뜻이므로, 번역은 **중복을 묶어 한 번만** 하고
여러 자리에 반영해야 한다.

### 7.16 슬롯 검출기 완성 — `tools/slots.py`

`python tools/slots.py work/jp1/TWN_ZOAH.PRG work/jp1/EVTZOAH.FNT [-v]`

```
TWN_ZOAH.PRG: 슬롯 배열 66개 / 항목 460개
  대사 4869개 40230자  ->  잔재 제외 3840개 37366자
```
슬롯 크기 분포: **31 B 450개**, 29 B 5개, 23 B 5개.
미해독이 든 문자열 비율 **23.4% → 4.3%**, 다른 구간의 정당한 대사 손실은 거의 없다
(`0x13146` 399→399, `0x36F9A` 335→335, `0x49544` 손실 0).

**검출은 세 판정을 AND 로 건다.** 하나씩으로는 전부 부족했다.

| | 판정 | 없으면 생기는 일 |
|---|---|---|
| (1) | 항목 시작이 **정확히 등간격** | — |
| (2) | 슬롯 내부 조각이 **(2a) 미해독 리드 바이트로 시작**하거나 **(2b) 다른 문자열의 중간에서 잘려나온 것**(그 바이트열이 배열 앞쪽에 있되 어느 발견 위치도 문자열 시작이 아님) | (1)만 쓰면 우연한 등간격에 진짜 대사가 걸려 통째로 잘린다 (`0x13146` 399→264) |
| (3) | 슬롯 경계 항목끼리 **서로 다르고 비어 있지 않다** | `0x13146` 은 **가변 배치 메뉴**(간격 11·11·19·17)인데 step=94 가 우연히 4개 맞았다. 그때 뽑힌 4항목 중 2개가 같은 문자열이었다 — 진짜 메뉴라면 없는 일이다. `0x49544` 의 빈 문자열 연속(step=16)도 여기서 걸린다 |

만드는 동안 밟은 함정 셋 — 전부 «검출기가 조용히 0건 또는 전건을 내는» 종류다:

1. **파일명 문자열은 후보에서 빼야 한다.** `T_JB_040.PCM` 은 12자+종단 = **13 B 고정**이라
   여러 개가 연달아 나오면 그것만으로 완벽한 등간격이 된다. 안 빼면 `0x49544` 구간의
   대사 127개가 전부 «잔재»로 몰려 사라진다.
2. **잔재가 자기 자신을 원본으로 센다.** `data.find` 결과에 자기 위치가 포함되고 그건
   당연히 문자열 시작이라, 모든 잔재가 «정당»으로 판정돼 **배열이 0개** 나왔다.
3. **잔재 후보끼리 서로의 근거가 된다.** 같은 꼬리 잔재가 슬롯마다 반복되므로,
   판정 대상 집합에서 빼지 않으면 서로를 «정식 저장»으로 가리키며 역시 0개가 된다.

검증 — 검출된 배열을 눈으로 확인했다.

```
0xC8B3 step=29 n=5   (体裁のいいものじゃないな) / 戦いに役立ちそうな物 / …
   ↳잘림  ないな)  ないな)  <!F8>  ないな)
0x2AB12 step=23 n=5  シャブリの… / 【49】【439】 / … 
   ↳잘림  <!94>リの【281】【361】【439】…  ×3
```
`0xC8B3` 에서 잘린 `ないな)` 는 §7.7 에서 «1바이트 토큰» 판정의 근거로 썼던 바로 그
조각이다. 정체가 **슬롯 꼬리 잔재**로 확정됐다.

### 7.18 ★★분량을 5만 자 부풀리던 것 — SH-2 코드 안의 ASCII 데이터

`regions.find` 가 **printf 포맷 문자열 같은 ASCII 데이터를 대사 구간으로 오인**하고 있었다.
1바이트 토큰이 글리프 index `0x20~0x7F` 를 가리키므로(§7.7) ASCII 문자열이 그대로
«일본어 대사»로 렌더돼 눈으로도 안 걸러졌다.

```
ホニソムテなはよツ  →  p h a s e ␣ % 1 d      =  "phase %1d"
ハテヤテハな…はらツ  →  l e v e l ␣ : % 2 d    =  "level :%2d"
```

발견 경로가 재미있다 — 슬롯 검출기가 `step=12`·`step=20` 배열을 대량으로 잡길래
«오검출인가» 하고 열어봤더니, 오검출이 아니라 **고정 크기 ASCII 문자열 테이블**이었다.

**배제 규칙**: 구간의 1바이트 토큰 비율이 30% 를 넘으면 ASCII 데이터로 본다.
진짜 JP 대사에서 1바이트 토큰은 아주 드물다(§7.7, 첫 구간 757문자열 중 9건).
⛔ US 판에는 이 규칙을 쓰면 안 된다 — 거기는 1바이트가 본문의 주력이다
   (`regions.find(..., ascii_data=True)`).

### 7.19 슬롯 검출기 — 겹침 처리 세 번째 함정

§7.16 완성 뒤에도 `TWN_SEEK` 에 미해독 459개가 남아 있었다. 원인은 둘 다
«같은 메뉴가 항목을 빼가며 여러 벌 이어 붙는» 구조 때문이었다.

1. **배열이 차지한 바이트 범위를 통째로 소비하면 안 된다.** 다음 벌의 시작이 앞 배열의
   마지막 슬롯 안쪽에 들어와 통째로 건너뛰어진다. 소비할 것은 «슬롯 경계와 잔재»뿐이다.
2. **이미 잔재로 판정된 것도 «정식 저장»의 근거가 될 수 없다.** 앞 배열에서 잔재로
   확정된 「』の噂」가 다음 배열 판정에서 «문자열 시작에 정식 저장돼 있다»는 근거로
   쓰여, 첫 벌만 잡히고 나머지가 통째로 남았다. 전역 `dead` 집합으로 뺀다.

고친 결과 `TWN_SEEK` 는 배열 1개 → **32개(항목 393)**, 디스크1 전체 미해독은
**706 → 107개(0.9%)** 로 떨어졌다.

**짝 FNT 규칙 추가**: `BTL_A3_2.PRG` ↔ `BTL_A32.FNT` — **마지막 언더스코어를 뗀 이름**.
이걸로 BTL 계열 11개가 확정됐다.

여전히 짝 미확정인 모듈 (nmax 를 최대 폰트 758 로 가정하고 쟀다 — 수치가 덜 정확하다):
`1ST_READ` `CHANGE` `FLD_C8` `SNDTEST` `TITLE` `WORLD` `TWN_JIRI`
`TWN_E006/E011/E014/E021/E022`.
그 중 **`FLD_C8` 은 5,842자로 커서 짝을 확정할 값어치가 있다**.
짝 없이 남은 FNT: `EVEEXPL` `EVT000_1~5` `EVT002` `EVT004_2` `EVT008` `EVT016_1~3`
`EVT029` `FLD_T0` `ITEM` `MENU` `MENUBK` `SAVE` `SHOP` `WORLDMAP`.

부수 관찰: `TWN_E006/E011/E014/E021/E022` 와 `TWN_JIRI` 는 문자열이 20~25개뿐인데
글자가 1,574~1,615자다(문자열당 ~76자). 긴 지문 덩어리 — **무비 자막 후보**다.

### 7.25 ★★「원문 길이를 넘어도 되나」 — 절대주소 포인터가 걸린다

§7.13 에서 «문자열별 포인터는 없다»까지 확인했었다. 이번엔 그 위 단계를 봤다.

**JP↔US 대조가 오라클이다.** US 는 구간 크기를 바꿔 넣었으므로, 무언가를 가리키는
주소가 있다면 그만큼 값이 달라져 있어야 한다.

**(1) 구간 시작을 가리키는 포인터는 없다.** 구간 21개의 JP↔US 델타
(`+4, +616, +2112, … +14376`)를 알고, 「JP 에 값 `base+A_jp`, US 에 `base+A_us`」인
공통 `base` 를 BE32·LE32 로 전수 검색 → **0건**(같은 위치 기준도, 값 집합 기준도).

**(2) 그런데 절대주소 포인터는 존재하고, 파일이 커진 만큼 밀렸다.**

```
0x06000000~0x06200000 범위 값 (4바이트 정렬)   20,483개
  델타 +0        985개   값 0600CBFC..06090009
  델타 +14484    642개   값 06092B96..0609A968
  델타 +14504    289개   값 0609C730..060B513C
                          (파일 크기 차이는 14,507)
```

`0x0609xxxx` 는 새턴 **Work RAM High** 절대 주소다. 즉 PRG 안에 로드 후 주소가
박혀 있고, **텍스트가 길어진 만큼 뒤쪽을 가리키는 것들이 전부 갱신됐다**.
밀린 것들은 마지막 텍스트 구간의 델타(+14,376)보다 큰 값만큼 밀렸으므로
**텍스트 영역 «뒤»를 가리킨다**.

**결론 — 실용적으로는 원문 길이를 지키는 게 안전하다.**

| 종류 | 늘려도 되나 |
|---|---|
| `slot` 항목 | ⛔ **안 된다.** 고정 간격이라 다음 항목을 침범한다 |
| 그 밖의 텍스트 | ⚠ 늘리면 **뒤를 가리키는 절대주소 포인터 ~931개를 전부 갱신**해야 한다. 공식 영문판 빌드는 그렇게 했다(재컴파일). 우리가 하려면 **로드 베이스를 확정**하고 포인터 재배치기를 만들어야 한다 — 아직 못 했다 |

로드 베이스는 `0x06052F34 ~ 0x06054F34` 로 좁혀졌지만 **확정 못 했다**.
(델타 0인 985개 중 상당수가 이 가정에서 텍스트 구간 중간을 가리키게 되는데,
 밀리지 않았다는 사실과 모순된다 — 그 985개는 텍스트가 아닌 다른 것을 가리키는
 것으로 보이나 확인 안 했다.)

→ 1차 목표는 **원문 길이 안에서 번역**. §7.7 의 **1바이트 토큰 슬롯을 한글로
   재활용**하는 것이 예산 확보의 핵심 수단이다(같은 글자가 2 B → 1 B).

### 7.27 ★★`MOVIE.DAT` — 무비 자막을 통째로 빠뜨리고 있었다

실기 스크린샷 9장으로 대조하니 **8장의 대사가 우리 텍스트에 없었다**.
`census.py`·`export.py` 가 **`.PRG` 만 스캔**하고 있었기 때문이다.

무비 자막은 전부 `MOVIE.DAT`(22,716 B)에 있다. **무비 47개 / 자막 1,604개 / 9,822자.**

**구조 (실측)**

```
[자막 텍스트 문자열들][큐 레코드 8 B × N][FF FF 00 00 00 00 00 00]   ← 무비 1개
[자막 텍스트 …        ][큐 …            ][FF FF …               ]   ← 무비 2개
…
```
큐 레코드 = `BE16 시작프레임, BE16 끝프레임, BE16 플래그(관측 전부 0x0025),
BE16 **그 블록 안 자막 오프셋**`. 첫 레코드 오프셋이 0 이라 텍스트가 블록 맨 앞이다.

**무비 ↔ FNT 짝은 `MOVIE.PRG` 가 준다.** 그 안에 `EVT000_1.CPK` … CPK 목록 50개가
순서대로 있고, **CPK 이름이 곧 `.FNT` 이름**이다. FNT 가 있는 47개가 자막 블록 47개와
정확히 1:1 로 대응한다.

검증 — 스샷 8장의 대사가 전부 `EVT008` 블록에서 나왔다.

```
000E0F  生きてたのか…よく無事で…
000E3C  奴らは谷にそって…北へ向かってる…
000E5F  あの男…クレイメン達を追え…
000E7C  本物の帝国軍が来る前に…
000EA4  誰なんです、そいつは！？
000EC6  なんで追わなきゃならないんです！？
000EE9  帝国の特務部隊…
000EFA  黒い艦隊を率いる男の話を聞いた事がある
```

★교훈: **스크린샷 한 장이 스캔 백 번을 이긴다.** 「`.PRG` 에 텍스트가 있다」는 초기
관찰을 그대로 믿고 `.DAT` 를 한 번도 스캔하지 않았다. 모집단이 맞는지는
**실기 화면과 대조**해야 알 수 있다.

→ 디스크1 총 분량 = 142,005 + **9,822** = **151,827자**.

### 7.29 ★★★`COMMON.DAT` 는 «장면마다 폰트가 바뀐다»

가장 비쌌던 함정. 두 단계로 틀렸다.

**(1) 파일 하나에 폰트 하나가 아니다.** `COMMON.DAT` 는 구간마다 다른 FNT 를 쓴다.

```
0xA760..0xBFC3  아이템 설명 209문자열 → ITEM.FNT (299글리프)
0xD0D9..0xD46A  메뉴 항목   53문자열 → MENU.FNT  (31글리프)
```
`ITEM` 하나로 읽어서 「性能を見る」가 「性LnをKnる」로 나왔고 원문 검색조차 안 됐다.
구간별로 «최대 글리프 index + 1 = FNT 글리프 수»인 폰트를 골라 해결.
⚠후보가 여럿이면 **`EVT*` 를 먼저 뺀다** — 무비 전용 폰트라 PRG·COMMON 이 쓸 리 없는데
  글리프 수가 같다는 이유로 `EVT043` 이 뽑혀 「性能を見る」가 「性顔を少る」로 읽혔다.

**(2) 그것으로도 부족했다 — 장면 FNT 를 아예 쓰면 안 된다.**
`COMMON.DAT` 는 상주 데이터라 그 문자열이 **어느 화면에서 그려질지 정해져 있지 않다**.
화면마다 다른 `.FNT` 가 물리므로 FNT index 를 쓰면 엉뚱한 글자가 나온다.
실제로 「판매」를 `MENU.FNT[2]` 에 넣었더니 다른 폰트가 물린 화면에서 **「판승」**으로 나왔다.

★**원본이 증거였다** — `売却できるアイテムのリストを表示` 는 전부 기본 폰트 글자로만
  돼 있다(`売`·`却` 이 기본 폰트에 있다). 개발진도 이 구간엔 장면 FNT 를 안 썼다.
→ 빌더는 `COMMON.DAT` 에 쓰이는 글자를 **반드시 기본 폰트에** 배정하고,
  못 들어가면 빌드를 실패시킨다.

### 7.6 미해결 (세션 2 시점)

| 항목 | 현재 상태 |
|---|---|
| US 영문 폰트 위치 | 미확정. COMMON.DAT의 16×16 1bpp/32B 포맷에는 없다. 4bpp·가변폭·압축 가능성. ASCII 순서 폰트 스캔(글리프 8~32B)은 노이즈만 나왔다 |
| ~~`0x22862` 구간 잔재~~ | ✅ **규명 완료 — §7.15** (고정 슬롯 배열의 죽은 꼬리) |
| ~~`tools/slots.py` 정확도~~ | ✅ **완성 — §7.16** (세 판정 AND, 미해독 23.4%→4.3%) |
| 남은 미해독 0.9% | 디스크1 전체 **107개**. 대부분 검출 기준(항목 4개 이상)에 못 미친 작은 슬롯 배열의 잔재다 — `FLD_A5` 의 `<!9C>` 3개는 간격 40·40, `FLD_B5` 의 `<!90>` 3개는 간격 23·23 으로 명백히 슬롯인데 항목이 3개뿐이라 안 잡힌다. 일부는 ASCII 데이터 잔여(`FLD_B2`) |
| ~~짝 FNT 미확정 13개 모듈~~ | ✅ **확정** — `FLD_C8`↔`FLD_T0`(229), `WORLD`↔`WORLDMAP`(39), `1ST_READ`↔`SAVE`(50), `TWN_E0xx`·`TWN_JIRI` 12개↔`EVEEXPL`(185). **«PRG 가 쓰는 최대 글리프 index + 1» 이 FNT 글리프 수와 정확히 맞는 것**을 후보로 잡고 렌더해 확인했다. 남은 미확정은 `CHANGE`·`SNDTEST`·`TITLE`뿐이고 셋 다 텍스트가 거의 없다 |
| ~~디스크 2~4~~ | ✅ **완료 — §7.20** (텍스트는 사실상 디스크1에 다 있다) |
| 제어코드 인수 폭 | 26종을 세었지만(§7.11) 인수를 갖는 코드가 있는지 모른다 |
| 로드 베이스 확정 | §7.25. `0x06052F34~0x06054F34` 로 좁혔으나 미확정. 이걸 확정해야 포인터 재배치기를 만들어 «원문보다 길게» 넣을 수 있다 |
| 화면 폭 예산 | 아직 안 쟀다. US 가 대사를 줄 단위로 쪼갠 게 흔적이다 |
| JP↔US 문자열 1:1 정렬 | 아직. US 는 `(It's very decorative,` / `and it is certainly not portable.)` 처럼 **줄 단위로 문자열을 쪼개** 개수가 어긋난다. PCM 파일명 앵커로 맞출 것 |
| ⚠ US 구간 탐지는 부실하다 | `regions.py` 는 «2바이트 글리프 토큰»으로 시작하는 곳만 후보로 삼는다. US 는 본문이 대부분 1바이트 토큰이라 그렇게 시작하는 구간을 놓친다(초기 ASCII 스캔에서 잡혔던 `0x24DD1` 구간이 US 결과에 없다). JP 결과는 이 결함의 영향을 받지 않는다 |
| ~~장면 FNT 한자 판독~~ | ✅ **완료 — §7.22** (101개 FNT, 8,830 글리프 100%) |
